## 評価を始める前に決める

| 決めること | 記入欄 |
| --- | --- |
| 評価で答える業務の問い | ［記入］ |
| 必須項目と任意項目 | ［記入］ |
| 比較対象と同一にする条件 | ［記入］ |
| 入力の範囲、データの種類と量 | ［記入］ |
| 成功条件、失敗時の中止条件 | ［記入］ |
| 実行担当・DBA・承認担当 | ［記入］ |
| 証跡の社内保管先・保存期間 | ［記入］ |
| 再実行時に固定するもの | ［commit、profile、lock、seed、入力hash、snapshot等］ |

判定は「未実施」「合格」「条件付き」「不合格」「対象外」から選び、対象外には理由を記します。任意機能の未起動を障害と数えたり、実施していない試験をCIの成功で代用したりしません。

## 評価用と会社データ用の環境を分ける

合成データ用と会社データ用は別のCompose/appName・volume・private設定・landingを使います。単にlandingを空にしても既存Bronzeは消えません。初回の隔離 `verify` は通常の業務namespaceを書き換える試験ではありません。[初回構築](../START-HERE.md)・[会社での受入](../COMPANY-ROLLOUT.md)

SQLへの通常素材投入は専用DEMO DBの新しいschemaへINSERTする操作です。CDCの固定I/U/Dは、管理者が用意した専用DBと所有権tokenを使う別操作です。SOURCE業務DBをダミーの書込み先へ使いません。

## 1. 配置・通信・認証

| ID | 確認する問い | 操作・観測 | 成功条件の候補 | 記録する証跡 |
| --- | --- | --- | --- | --- |
| DEP-01 | 公開Gitから同じ構成を取得できるか | 確認済みcommitを取得しlockを照合 | ソースとlockが選択commitに一致 | commit、hash、profile |
| DEP-02 | 管理対象を取り違えないか | Dokployの確定appName、private env、volumeを照合 | 同じ一つの環境を指す | 匿名化した対応表 |
| DEP-03 | 起動順とone-shotが正しいか | Containersと各healthを確認 | migration等が0終了、常駐serviceが起動 | 時刻、対象、状態 |
| NET-01 | image pullが許可経路を使うか | daemonのproxy/CAでpull | 必要imageが取得可能 | 許可先区分、結果 |
| NET-02 | buildの依存取得が可能か | 企業CA付き/なしの選択条件でbuild | checksumを維持したままbuild成功 | buildの対象commitと終了結果 |
| NET-03 | 内部通信がproxyへ流れないか | 内部S3/catalog/Trinoの実通信 | 期待した内部経路で到達 | client・宛先役割・結果 |
| SEC-01 | 操作APIに認証が必要か | tokenなしと正規tokenを別要求 | 未認証を拒否し、正規要求は実行可能 | status、秘密を除いた応答 |
| SEC-02 | SSRF例外が必要な先だけか | 許可workerと未許可内部先を比較 | 正規workflow成功、未許可を拒否 | node・status・例外範囲 |

[配置](../DOKPLOY.md)・[proxy](../COMPANY-PROXY.md)・[SSRF](../SSRF.md) を使います。proxy、NO_PROXY、SSRF、TLSの信頼は別々の条件です。GUIの接続診断だけでdaemonや全Java clientまで検証できたとは扱いません。

## 2. 素材・品質・メダリオン

| ID | 確認する問い | 操作・観測 | 成功条件の候補 | 記録する証跡 |
| --- | --- | --- | --- | --- |
| DAT-01 | 投入だけで下流を書き換えないか | GUIで合成batchを1回生成 | manifest/6素材を生成、Goldは未変更 | run ID、原本hash、前後snapshot |
| DAT-02 | コピー途中の素材を扱わないか | readyなし/正常ready/hash不一致を試す | 未完成を無視、不一致を拒否 | ケース、対象相対名、結果 |
| DAT-03 | 原本へ戻れるか | 原本を取得し元bytes/hashと比較 | 同一byte列とSHA-256 | hashと照合結果 |
| DAT-04 | 改訂・重複を二重計上しないか | 同じ業務キーの過去/改訂/重複を入力 | 最新候補だけを採用 | 対象キー範囲、Silver/Gold値 |
| DAT-05 | 不正な最新版を説明できるか | 型不正の新しい版を入力 | 理由付き隔離、古い正常版へ戻らない | 元文字列、理由、採用結果 |
| DAT-06 | 集計でJOINの行増幅が起きないか | 複数実績/停止/分納を含む入力 | 独立計算と数量/金額が一致 | 入力範囲、独立集計、差分 |
| DAT-07 | 再取り込みが再計上を起こさないか | 同じ完成ファイルを再実行 | skipと同じ業務集計 | imported/skipped、前後値 |
| DAT-08 | 合成の固定期待値を再現できるか | 隔離verifyを実行 | 11検査成功、2回目7件skip | ok、checks、fixture条件 |

[異常26ケース](../ANOMALY-SCENARIOS.md) を一つずつ試してから組み合わせます。不良急増・将来時計・過剰出荷等は現ルールで有効値として採用される場合があり、全てが自動隔離されるわけではありません。通常のGUI runは独立IDで追加されるため、別runの累積合計を同一対象の差分と混同しません。

## 3. 会社SQLとCDC

| ID | 確認する問い | 操作・観測 | 成功条件の候補 | 記録する証跡 |
| --- | --- | --- | --- | --- |
| SQL-01 | read-only接続が成立するか | 名前解決/TCP、TLS、認証、SELECTを順に確認 | 必要6表/列だけを抽出可能 | 接続条件の区分と各段階の結果 |
| SQL-02 | 抽出が契約へ正しく対応するか | DBAの同一範囲集計と6素材を比較 | 件数・NULL・日時・数量が一致 | map版、抽出manifest、照合差分 |
| CDC-01 | 初回snapshotが現在値へ反映されるか | Connector RUNNING後に各層を照合 | 全対象主キーの現在値が一致 | LSN/offsetと対象範囲 |
| CDC-02 | I/U/Dが伝わるか | 専用検証DBで各操作を順次実行 | raw/現在値/Silver/Goldで対応が一致 | 操作順、commit、各層の差分 |
| CDC-03 | consumer再起動で増殖しないか | checkpoint/offsetを保持して再起動 | 既処理raw重複なし、現在値が一致 | 前後distinct、lag、checkpoint |
| CDC-04 | DDL変更・停止期限へ対応できるか | DBAと別試験を計画 | 合意した停止/復旧/再snapshot手順を満たす | 保持設定、停止期間、復旧結果 |

CDC-04は同梱キットで自動解決する機能ではありません。複合主キーや自動schema追従は未対応です。保持期間を超える停止、DBの復元、capture instance変更などは別の運用評価へ含めます。[SQL抽出](../SOURCE-SQLSERVER.md)・[CDC](../CDC.md)

## 5. 性能・容量・復旧を測る場合

| ID | 評価の条件 | 記入する測定値 | 判定に必要な比較 |
| --- | --- | --- | --- |
| PERF-01 | 固定入力量、固定同時実行、cold/warmを分離 | 各回の経過時間、行/byte、成功/失敗、資源 | 合意した許容時間、同条件の現行方式 |
| PERF-02 | CDC操作時刻から参照可能時刻までを定義 | 各イベントの時刻差、件数、lag、時計差 | 合意した鮮度、停止後の追随時間 |
| CAP-01 | 保存期間、snapshot/原本保持、増分を定義 | data/metadata/DB/log別の増加量 | 利用可能容量、必要保持日数 |
| REC-01 | 書込み停止点と一組のbackupを固定 | 復元開始/完了、欠損範囲、照合結果 | 合意したRPO/RTO、原本hash/表/GUIの一致 |
| OPS-01 | 通知先と担当、対象と閾値を定義 | 異常発生/検知/通知/着手の時刻 | 合意した検知・対応時間 |

未測定値は空欄または「未測定」とします。Composeのmemory上限は実使用量ではありません。静的CI、small smoke、volume再起動保持から性能・HA・復元時間・費用効果を算出しません。

## 終了時に揃えるもの

1. 評価条件、合意した成功条件、実施/対象外の一覧。
2. 実行commit、入力manifest/hash、照合に使ったSQLや期待値の版。
3. 観測結果と根拠ID、失敗・再試行・未評価の理由。
4. 図と本文の対応、一般化した画面、秘密を除いた共有版。
5. 次段階の判断、残課題、担当と期限。必要なら [意思決定記録](DECISION-RECORD-TEMPLATE.md) を作成。

## 初心者向けの実施順序

最初の周回では配置/core、合成batch、固定verify、GUI、停止・再開の順にします。ここが通ってから、会社SQL、CDC、Spark remote、AI、性能、復元を追加します。任意機能をすべて同時に有効化して、失敗箇所が分からなくなる状態を避けます。

各評価IDの候補を社内の成功条件へ具体化します。「速い」「正しい」だけでなく、対象と閾値、許容差、失敗時の判断を事前に決めます。既存の合成期待値を、会社の業務値の正解として使いません。

| 結果の状態 | 記入すること |
| --- | --- |
| 成功 | 条件、観測値、期待値、証跡、判定者 |
| 失敗 | 最小再現、差分、影響、再試験条件 |
| 中止 | 中止した段階、理由、残った書込みや復旧の必要性 |
| 未実施 | 前提不足、担当、次に実施できる条件 |
| 対象外 | 今回の目的から除く理由、将来の扱い |

## 上級者向けの比較設計

正解側のSQLは、検証対象のSQLをそのままコピーせず、業務担当/DBAによる同一範囲の独立集計と突き合わせます。主キー、時刻境界、単位、NULL、分納/改訂/削除を揃えます。CDCではrawイベント数と現在値件数を区別し、再起動前後のdistinctとcheckpointも記録します。

性能は入力hash、各回の時刻、各サービスの資源、cold/warm、同時実行を記録し、複数回の結果と失敗数を残します。単発の最良値だけを代表値にしません。復元はbackupファイルの存在確認から進み、別環境での表・原本・鍵・GUI保存物の照合までを一つの評価とします。

評価条件を変更したときは新しい版を付け、変更前の結果へ新しい成功条件を遡って適用しません。根拠は [EVIDENCE-MATRIX](EVIDENCE-MATRIX.md)、追加開発の境界は [CUSTOMIZATION](../CUSTOMIZATION.md) へ結び付けます。
