## 実行順と境界

PR 1 は [棚卸し](CURRENT-ARCHITECTURE-INVENTORY.md)、[Consumer 評価](CDC-CONSUMER-ASSESSMENT.md)、[業務境界](DOMAIN-BOUNDARIES-DRAFT.md) と本計画のみ。現行 Debezium/Connect、capture、offset topic、Iceberg/Cloudflare、実サービスの設定・配備は変更しない。外部リリースへの依存維持は、別件のイメージ供給対策へ分離する。

| 順序 | 可逆な作業・採用理由 | 受け入れ／停止条件 | 戻し方 |
|---|---|---|---|
| PR 1 証拠と計画 | 両ブランチの別の基準 SHA で棚卸しし、技術責務・データ・人の判断を可視化 | 四文書と登録・索引だけ。現状、予定、未知の区別、リンク、公開情報を独立レビュー | 文書 PR の通常の revert。データ変更なし |
| PR 2 UI 非依存の検証 | UI/BFF を含まないサービス選択で核心経路を隔離。main #34 の静的検査は再実装せず、実経路を補う。UI は PoC 管理用に維持 | UI の実行なしで取り込み・保存・変換・クエリが成功し、設定変更は宣言的入力で再現できる。別途 GUI が従来の操作を満たす。失敗は独立の観測点で見える | テストの revert。動作変更が必要なら別 PR、同じ API/CLI/権限を維持した切戻し |
| PR 3 現行 Consumer の Raw 責務切出し | 現行の処理と名前空間を残し、合成環境の Raw-only 経路を作って入力と結果の責務を分離 | 既存／試験経路を同じ入力で比較。主経路の ack・設定・offset・永続状態に差がないこと。Raw-only の再起動・再実行が同一の結果 | 試験経路を撤去し、既存の単一 writer を維持 |
| PR 4 標準 Sink を別 namespace で評価 | オープンな形式・宣言的 routing を活用し、自作 poll/write の置換余地を測る | 公式仕様で版・catalog、schema evolution、commit/offset の要求を確認。別 group/namespace/ACL で再送・復元を実測。採用不能なら PR を拡大せず ADR を残す | 比較側だけ停止、別権限で後片付け。既存 capture・group・本表を変更しない |
| PR 5 変換を宣言的 SQL へ | 現行 SQL の意味・集計を保ち、必要箇所で Spark 等と比較。Silver/Gold/Quarantine と Current State の責任を切り分ける | 業務側レビュー後、合成 fixture の版、並び、削除、遅着、隔離理由、同一粒度の集計・品質が旧経路と同値。利用者互換と代替コスト確認 | 旧 SQL・読取先を残したまま実験側だけ停止。既存公開テーブルの名前や権限を変えない |
| PR 6 不要になった Consumer 責務を縮退 | 並行試験と観測期間の後、重複ラッパー・運用ポイントを減らす。機械的なコード削除はしない | 未依存を CLI/API の実利用でも確認。受け入れ・復旧演習の承認、切戻し期限、保持、責任者が揃う。重大な差異、未検証、同時 writer の可能性で停止 | 新 writer を止め、整合した復旧点と控えの設定で旧側に戻す。事後照合後に再開 |

PR 3〜6 の番号は計画上の順番であり、既存 GitHub PR 番号ではない。PR 2 以降は個別レビューで変更範囲を再承認し、main と Vision を別環境・別差分として評価する。一方の試験を他方の結果と見なさない。低リスクの表示共通化は両方で既に対応済み。未使用・統合候補は外部利用の調査後に追加する。

## 実験前の証拠をそろえる

1. 基準と候補の SHA、公開安全な構成、seed、schema/イメージ版、利用する権限、比較 namespace を記録する。使い捨て SQL Server 2022/Kafka/Iceberg、環境固有値を含まない合成 fixture を使い、現用環境にアクセスしない。再現できる隔離環境がなければ対象段階を止める。
2. Before/after に同じ既知イベントを流し、各境界の raw ID 集合、source の順序、状態・削除、件数、欠落/重複、計算結果、隔離・許可拒否を保存する。障害を raw 前後、SQLite stage 後、派生途中、ローカル完了後、Kafka ack 前後で起こし、再開時の差を比較する。
3. UI 停止相当試験では設定・データ経路・管理経路を別々に判定する。CLI/API の明示構成で core 経路の実測を取り、UI 管理操作が利用できないことを正常な隔離として区別する。Compose の静的グラフだけではこの gate を通さない。
4. 運用比較では独自デーモン/API、共有状態、重複定義、人手工程、機械確認可能な操作、別担当者の引継ぎ、復旧時間を計測。費用・追加サービス・権限面は公式仕様と計測なしでは未確認。BI/AI へ拡張する場合は個別に read-only 境界、鮮度、出典、権限を試験する。

## 将来の切替と復元の条件

- 切替責任者・承認者、停止条件、復旧時間と欠損許容範囲は業務側と決める。合意・隔離復元・ロールバック演習なしで配備しない。現段階で担当者や許容値は未決。
- 一貫する復旧点に、SQL Server capture/LSN と保持、Connect の config/offset/history、Kafka topic/group と利用可能な最小・最大 offset、SQLite state/checkpoint、Iceberg catalog と warehouse snapshot、必要に応じて管理 journal/D1 revision と秘密の参照手順を対応付ける。別々に取った snapshot を一括 transaction とみなさない。秘密値そのものは成果物・ログに格納しない。
- 停止した writer の時点を固定し、旧 writer の排他停止確認後にのみ、対応した復旧点で再開する。欠落、誤重複、削除復活、権限差、名前空間違い、保持範囲外、メトリクス未観測があれば切替を中止。自動 offset reset や既存 volume/capture/connector の削除で解決しない。
- 別の担当者が手順から構成を再現し、元経路の復元と再送を実演する。新方式が原表の復元、監査、閲覧権限を維持できなければ PoC にとどめる。

現時点で確認済みなのは Git 管理の構成・コードと試験の対象範囲であり、UI 停止下の稼働、別 Sink、移行、実データ、費用の合格を示すものではない。
