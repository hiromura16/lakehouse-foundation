## 仮のコンテキスト図

以下はリポジトリ中の公開サンプルに基づく仮説であり、実業務の境界、責任者、システム名、正本は未確定。名詞の一致だけで同じモデルに統合しない。アプリケーション名や配備単位を先に増やさず、まず SQL/契約/fixture の境界を明確にする。

| 仮の境界 | サンプル・根拠 | 契約と未決の業務判断 |
|---|---|---|
| ソース契約／技術取り込み | `infra/source/sqlserver-tables.example.json`、`infra/sqlserver/002_demo_tables.sql`、`medallion/sources.json` | source/capture identity、送達位置・原文・版、観測時刻を残す。変更行は業務イベントの確定とは限らない。アクセス範囲、保持期間、ソース公開責任を確認 |
| 製品・製造計画 | デモの `erp_products`、`erp_work_orders` | 製品識別子、指図作成/改訂/取消、計画単位を確認。指図の正本、変更履歴、実績が確定する境界を確認 |
| 製造実績・設備稼働 | デモの `mes_events`、`mes_downtime` | イベント時刻と受付時刻、実績・停止区間の開始/終了、再処理、重複・遅延・日跨ぎ時の計上を確認。品質/保全と同じ責務と決めない |
| 販売・出荷 | デモの `erp_sales_orders`、`erp_shipments` | 受注、分割出荷、訂正・遅着、返品の意味、粒度と期限・正本を確認。製造計画との関係は ID とバージョン付き契約で表す |
| 品質・保全・物流 | 本段階で実業務モデルを確定する証拠なし | 不良・再検査・保全はインタビュー候補。試験品質チェックや quarantine を、部門の品質業務そのものと見なさない |
| 読取モデル／運用管理 | `medallion/03_gold.sql` の製造日次・受注出荷のサンプル、CLI、Vision 管理 API | Gold は目的別の用途と粒度を明記。管理 UI/設定 DB から生産実績の正本を作らない。業務データと承認・監査の責任を分ける |

`取得・配信 → Bronze の観測事実 → コンテキスト別 Silver/隔離 → 用途別 Gold → BI/AI 読取`。時間、版、欠損、削除、許可された利用を契約で表現し、ソース固有コードは変換境界に局所化する。別コンテキストの内部 DB や内部表に直接結合しない。main と Vision は論理用語、スキーマ、品質例、fixture を共有候補とし、認証・カタログ・ストレージまで共通フレームワークに押し込まない。

## 知識を得て承認するための最小手順

1. 対象を一つ選び、ドメインエキスパート（現場用語/例外）、業務オーナー（目的・受け入れ）、データ責任者（定義・正本・権限・保持）、実利用者（利用・訂正例）、基盤担当（境界・復元・証拠）を役割として特定する。担当者未特定の段階で実名や組織名を仮置きしない。
2. 60〜90 分を目安に 1〜3 回、イベント探索を実施する。正常な発生/承認/訂正のほか、取消、遅延、欠損、二重登録、再送、部分完了を技術イベントと業務イベントに分ける。各イベントの正本、オーナー、状態遷移、粒度、時刻、鮮度・品質目標、公開と保持の許容範囲を同じ表に記録する。
3. 人名、実データ、内部システム識別子は公開に含めない。公開 Git には再現可能な合成 fixture と、合意済みの一般化された用語・契約・承認条件だけを残す。現行の `medallion/checks/` にある遅着/改訂・日付・結合多重化などの検査と並べ、何を証明していないかも残す。
4. 契約の例: 「事実 ID／ソース版／イベント時刻と観測時刻／訂正・取消の表現／権限と保持／gold の粒度／再実行同値条件／確認者」。データ責任者が公開範囲と例外、業務オーナーと実利用者が読取モデルの受け入れを確認するまで正式用語、物理分割、本番仕様とはしない。
