# レビュー指摘を改善へ取り込む

GitHubのissue、PR review、修正依頼文書から、対象commitと根拠を確認して修正します。同時作業では、未コミット変更や他の担当者のcommitを破棄・上書きせず、実際の差分を確認します。

## 指摘に含める情報

| 項目 | 内容 |
| --- | --- |
| 対象 | 公開commit、branch、ファイルと行、必要なprofile |
| 問題 | 再現する操作、実際の結果、期待する結果 |
| 根拠 | 採用版の公式資料・コード・合成試験。推測と事実を分ける |
| 優先度 | 影響、再現条件、データ/互換性/機密への関係 |
| 修正の確認 | 何が通れば解消と判断できるか |

社内URL、実IP、proxy、資格情報、企業CA、業務データ、生ログは掲載しません。必要な再現入力は一般化した最小の合成値にします。図の指摘は図IDとpanel/edge、キャプションの該当箇所も示します。

## 取り込みの順序

1. issue/文書の対象commitと現在のmain・作業branchを照合します。新しいcommitですでに解消している場合は重複修正しません。
2. 指摘を実装・採用版の公式資料・最小再現で確認します。提案に従う場合も、秘密の公開や既存データ破壊を伴う操作は別に扱います。
3. 修正範囲と担当を揃え、他の変更と同じファイルを扱う場合は差分を確認します。無関係な変更をまとめて戻しません。
4. 関連コード、説明、図、期待値を整合させ、必要なテストと公開前の機密検査を実行します。
5. PRへ対応するissue/文書、変更理由、検証結果、未解決点を記載します。未実施の実会社確認やOffice描画を成功扱いにしません。
6. merge直前にもmainと新着reviewを確認します。mainが進んでいれば差分を統合し、影響する検査を再実行します。

図・exportの編集規約は [編集ガイド](reports/EDITING-GUIDE.md)、機密情報の境界は [公式資料・文書監査](REFERENCES.md)、既存の機能検証は [VALIDATION.md](VALIDATION.md) を参照します。作業中の新着確認と、常設の自動監視を区別します。

具体的な指摘・原因・修正・回帰の例は [REVIEW-FOLLOWUP](REVIEW-FOLLOWUP.md) にあります。レビュー文書を読むだけでなく、再現と受入条件を実装へ結び付けます。
